部署 ​

本指南涵盖将 AdonisJS 应用部署到生产环境。你将了解到如何：

  • 理解独立构建以及为什么生产环境不需要源文件
  • 在构建和运行时正确配置 NODE_ENV
  • 使用 node ace build 命令创建生产构建
  • 配置要复制到构建输出的静态文件
  • 在生产环境中运行你的应用
  • 使用持久化存储处理用户上传的文件
  • 为生产环境配置日志
  • 在生产环境中安全地运行数据库迁移
  • 使用多阶段 Dockerfile 创建 Docker 镜像

概述 ​

AdonisJS 应用使用 TypeScript 编写，在生产环境运行前必须编译为 JavaScript。构建过程会创建一个独立构建，这意味着编译输出包含运行应用所需的一切，而无需原始的 TypeScript 源文件。

由于 AdonisJS 应用运行在 Node.js 运行时上，你的部署平台必须支持 Node.js 24 或更高版本。构建过程会编译你的 TypeScript 代码、打包前端资源（如果使用 Vite），并将必要的文件复制到一个 build 目录，你可以直接将其部署到生产服务器。

理解独立构建 ​

独立构建是你的 AdonisJS 应用的编译输出。创建构建后，你只需将 build 目录部署到生产服务器。原始源文件、开发依赖和 TypeScript 配置在生产环境中都不需要。

这种方法有几个好处。由于不附带 TypeScript 源文件或开发工具，部署体积显著更小。生产环境只需要 JavaScript 运行时，你可以将 build 文件夹视为一个独立的、自包含的应用。

构建和运行时的 NODE_ENV ​

NODE_ENV 环境变量在构建过程和运行时的行为不同，理解这一区别对于成功部署很重要。

在构建过程中，你需要安装开发依赖，因为构建工具（TypeScript 编译器、Vite 和其他构建工具）通常在你的 package.json 中列为 devDependencies。如果你在依赖尚未安装的 CI 环境或沙箱中创建构建，请在运行 npm install 之前设置 NODE_ENV=development 以确保所有依赖可用。

sh
# 在 CI/CD 或全新环境中
NODE_ENV=development npm install
npm run build

在生产环境运行时，NODE_ENV 应设置为 production。这会启用生产优化并禁用仅开发的功能，如详细错误页面。

创建生产构建 ​

从项目根目录运行构建命令。

sh
npm run build

这在底层执行 node ace build。构建过程按顺序执行以下步骤：

  1. 如果存在现有的 ./build 文件夹，则将其移除
  2. 重写 ace.js 文件以移除 TypeScript 加载器导入
  3. 使用 Vite 编译前端资源（如果已配置）
  4. 使用 tsc 将 TypeScript 源代码编译为 JavaScript
  5. 将在 metaFiles 数组中注册的非 TypeScript 文件复制到 ./build
  6. 将 package.json 和你的包管理器锁文件复制到 ./build

如果你的代码中存在 TypeScript 错误，构建将失败。你必须在创建生产构建之前修复这些错误。如果你需要临时绕过 TypeScript 错误，请使用 --ignore-ts-errors 标志。

sh
npm run build -- --ignore-ts-errors

--package-manager 标志控制将哪个锁文件复制到构建输出。如果未指定，构建命令会根据你调用命令的方式（例如 npm run build 与 pnpm build）检测你的包管理器。

sh
npm run build -- --package-manager=pnpm

构建输出的内容 ​

成功构建后，build 目录包含你编译后的应用。以下是你会看到的内容：

  • 与源代码目录结构对应的编译后的 JavaScript 文件
  • 用于安装生产依赖的 package.json 和锁文件
  • 在 metaFiles 中配置的静态文件和其他资源
  • build/public 中的前端资源（对于由 Vite 驱动的应用）

环境文件（.env、.env.example）被有意排除在构建输出之外。环境变量在不同环境之间不可移植，你必须通过托管平台的环境变量管理为每个部署目标单独配置它们。

静态文件 ​

需要包含在生产构建中的静态文件通过 adonisrc.ts 文件中的 metaFiles 数组配置。这些是应用在运行时需要的非 TypeScript 文件，如 Edge 模板或公共资源。

ts
{
  metaFiles: [
    {
      pattern: 'resources/views/**/*.edge',
      reloadServer: false,
    },
    {
      pattern: 'public/**',
      reloadServer: false,
    },
  ],
}

pattern 属性接受用于匹配文件的 glob 模式。reloadServer 属性控制在开发期间文件更改是否触发服务器重启，对生产构建没有影响。

对于超媒体和 Inertia 应用，Vite 编译前端资源并将其放置在 public 目录中。这些资源随后在构建过程中被复制到 build/public。

为反向代理和负载均衡器调整 keepAliveTimeout ​

真实世界的应用通常不是直接访问的，而是在反向代理和负载均衡器（例如 Nginx）之后。

默认情况下，Node.js 在 5 秒后关闭空闲连接，但 Nginx 可能会尝试将它们保持打开 60 秒以上。当 Nginx 尝试复用一个它认为打开但 Node.js 已经静默关闭的旧连接时，Nginx 会抛出 502 Bad Gateway 错误。

为避免此问题，你需要将 AdonisJS 服务器的 keepAliveTimeout 改为大于 Nginx 的 proxy_read_timeout（默认 50 秒）。

ts
{
  keepAliveTimeout: 55000,
}

在生产环境中提供静态文件 ​

虽然 AdonisJS 包含一个静态文件服务器，但在生产环境中你应该将静态文件服务卸载到专用工具。由 Node.js 进程处理的每个静态文件请求，都是无法用于动态工作的请求。反向代理或 CDN 专为此任务而构建，将以更少的资源使用更快地交付文件。

根据你的基础设施，你有两个主要选择。

反向代理（Nginx、Caddy、Traefik、Apache）

配置你的反向代理，为静态文件请求直接提供 build/public 目录，并将其他所有请求转发到你的 AdonisJS 服务器。这样，静态文件永远不会到达你的 Node.js 进程。

使用 Nginx，你可以添加一个 location 块，尝试首先从 public 目录提供文件，并对动态路由回退到 AdonisJS 服务器。

nginx
server {
    listen 80;
    server_name example.com;

    root /path/to/your/app/build/public;

    location / {
        try_files $uri @adonis;
    }

    location @adonis {
        proxy_pass http://localhost:3333;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

CDN

为获得最佳性能，将编译后的资源上传到 CDN。这需要更新 Vite 配置中的 assetsUrl 选项，使生成的资源 URL 指向你的 CDN 而不是应用服务器。

ts
{
  assetsUrl: 'https://cdn.example.com/assets',
}

每次构建后，将 build/public 的内容部署到你的 CDN。你的 CI/CD 流水线可以自动化此步骤。

TIP

你可以结合两种方法。使用反向代理从 public 目录提供 favicon.ico 和 robots.txt 等文件，并使用 CDN 提供受益于全球分发的 Vite 编译资源（JavaScript、CSS、图片）。

运行生产构建 ​

要在生产环境中运行你的应用，请将 build 目录视为应用的根目录。切换到 build 目录，安装生产依赖，并启动服务器。

sh
cd build
npm ci --omit=dev
node bin/server.js

使用 npm ci --omit=dev 而不是 npm install 可确保仅使用锁文件进行干净、可重现的安装，并跳过开发依赖。你还必须在启动服务器之前提供所有必需的环境变量。你的托管平台应该有配置环境变量的机制。你可以参考 env.ts 文件或 .env.example 来查看应用需要哪些变量。

用户上传的文件 ​

用户上传的文件需要能在部署后存活的持久化存储。当你部署新版本的应用时，之前的 build 目录通常会被替换，这意味着存储在该目录本地的任何文件都会丢失。

对于生产部署，请使用云存储提供商，如 Amazon S3、Cloudflare R2 或 Google Cloud Storage。这些服务提供独立于应用部署的持久、耐用的存储。

如果你必须在服务器本地存储文件，请配置一个位于应用 build 文件夹之外的目录，并确保此目录在部署后持久存在。具体方法取决于你的托管平台和部署策略。

日志 ​

AdonisJS 使用 Pino 进行日志记录，它以 NDJSON 格式将结构化日志输出到 stdout。这种格式非常适合生产环境，因为大多数日志服务和日志聚合器可以直接解析 NDJSON。

配置你的托管平台以捕获应用进程的 stdout。大多数平台提供与 Datadog、Logtail 或 Papertrail 等日志服务的内置集成。或者，你可以将应用的输出通过管道传递给日志传输代理。

Pino 的结构化 JSON 输出包含时间戳、日志级别以及你附加到日志消息的任何额外上下文，使得在日志服务中搜索和过滤日志变得简单直接。

数据库迁移 ​

在生产环境中使用 migration:run 命令和 --force 标志运行迁移。

sh
node ace migration:run --force

需要 --force 标志，因为在生产环境中默认禁用运行迁移。这是一项防止意外模式更改的安全措施。

AdonisJS 迁移是幂等的并使用排他锁。如果多个进程同时尝试运行迁移（例如在滚动部署期间），只有一个进程会执行迁移，其他进程会等待。这防止了竞态条件和重复的迁移尝试。

如果你的部署平台支持生命周期钩子或有运行数据库迁移的专用机制，请使用它而不是将迁移作为应用启动的一部分运行。这种分离确保在任何应用实例开始服务流量之前迁移成功完成。

在生产环境中回滚迁移默认被禁用，且不推荐使用。与其回滚，不如创建一个新的迁移来撤销你需要撤销的更改。这种方法维护了所有模式更改的清晰历史，并避免了生产环境中回滚相关的风险。

Dockerfile ​

以下 Dockerfile 使用多阶段构建创建优化的生产镜像。第一阶段安装所有依赖并创建构建，而最终阶段仅包含生产运行时。

dockerfile
FROM node:lts-bookworm-slim AS base

# ----------------------------
# 阶段 1：安装所有依赖
# ----------------------------
FROM base AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

# ----------------------------
# 阶段 2：构建应用
# ----------------------------
FROM deps AS build
WORKDIR /app
COPY . .
RUN node ace build

# ----------------------------
# 阶段 3：生产运行时
# ----------------------------
FROM base AS production
WORKDIR /app
ENV NODE_ENV=production

COPY --from=build /app/build ./
RUN npm ci --omit=dev

EXPOSE 3333
CMD ["node", "bin/server.js"]

此 Dockerfile 遵循多阶段模式，每个阶段都有特定用途。deps 阶段安装构建所需的所有依赖。build 阶段编译 TypeScript 应用。production 阶段创建仅包含生产依赖的最小镜像。

要构建并运行 Docker 镜像：

sh
docker build -t my-adonis-app .
docker run -p 3333:3333 --env-file .env my-adonis-app

使用 --env-file 标志或单独的 -e 标志传递环境变量。容器默认暴露端口 3333，你可以将其映射到任何主机端口。

使用 Docker 运行迁移 ​

对于容器化部署，你有两种运行迁移的选择。你可以在启动应用容器之前将它们作为单独的命令运行：

sh
docker run --rm --env-file .env my-adonis-app node ace migration:run --force

或者，你可以创建一个入口脚本，在启动服务器之前运行迁移。在项目根目录创建此文件：

js
import { execSync } from 'node:child_process'

/**
 * 当设置了 MIGRATE 环境变量时，
 * 在启动服务器之前运行迁移。
 */
if (process.env.MIGRATE === 'true') {
  console.log('Running migrations...')
  execSync('node ace migration:run --force', { stdio: 'inherit' })
}

/**
 * 启动服务器
 */
console.log('Starting server...')
await import('./bin/server.js')

更新你的 Dockerfile 以使用此入口点：

dockerfile
FROM node:lts-bookworm-slim AS base

FROM base AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM deps AS build
WORKDIR /app
COPY . .
RUN node ace build

FROM base AS production
WORKDIR /app
ENV NODE_ENV=production

COPY --from=build /app/build ./
RUN npm ci --omit=dev

# 复制入口脚本
COPY docker-entrypoint.js ./

EXPOSE 3333
CMD ["node", "bin/server.js"]
CMD ["node", "docker-entrypoint.js"]

使用此设置，将 MIGRATE=true 设置为环境变量将在启动服务器之前运行迁移。对于多个容器同时启动的水平扩展，迁移锁定确保只有一个容器运行迁移，其他容器等待。
