保护服务端渲染应用 ​

本指南涵盖 AdonisJS 服务端渲染应用的安全功能。你将了解到如何：

  • 保护表单免受 CSRF（跨站请求伪造）攻击
  • 定义 CSP（内容安全策略）规则以防止 XSS 攻击
  • 配置 HSTS 以强制 HTTPS 连接
  • 使用 X-Frame-Options 头防止点击劫持
  • 禁用 MIME 嗅探以避免内容类型攻击

概述 ​

Web 应用面临持续的安全威胁。攻击者利用表单提交伪造、恶意脚本注入和点击劫持等漏洞来危害你的用户。@adonisjs/shield 包提供统一的防御层，保护你的服务端渲染 AdonisJS 应用免受这些常见攻击。

Shield 通过向应用添加安全相关的 HTTP 头和中间件来工作。Shield 不是单独配置每项保护，而是提供一个包含合理默认值的单一包，你可以根据需要自定义。所有保护都通过 config/shield.ts 配置，使审计和调整安全态势变得容易。

该包已预配置在 web 启动套件中。如果你需要手动安装，请确保先配置 @adonisjs/session 包，因为 Shield 依赖会话来存储 CSRF 令牌。

sh
node ace add @adonisjs/shield
查看 add 命令执行的步骤

  1. 使用检测到的包管理器安装 @adonisjs/shield 包。

  2. 在 adonisrc.ts 文件中注册以下服务提供者。

    ts
    {
  providers: [
    // ...其他提供者
    () => import('@adonisjs/shield/shield_provider'),
  ]
}

  3. 创建 config/shield.ts 文件。

  4. 在 start/kernel.ts 文件中注册以下中间件。

    ts
    router.use([() => import('@adonisjs/shield/shield_middleware')])

CSRF 保护 ​

CSRF（跨站请求伪造）攻击诱骗已认证用户在不知情的情况下提交恶意请求。想象一个用户已登录你的银行应用。在浏览另一个站点时，该恶意站点包含一个隐藏表单，向你的银行提交转账请求。因为用户的浏览器自动包含其会话 cookie，银行会像用户有意操作一样处理转账。

Shield 通过要求每次表单提交都附带一个秘密令牌来防止 CSRF 攻击。该令牌在服务端生成并嵌入你的表单中。由于攻击者无法从其恶意站点访问此令牌，他们的伪造请求将被拒绝。

保护表单 ​

配置 Shield 后，所有没有有效 CSRF 令牌的表单提交将自动失败。你必须使用 csrfField Edge 辅助函数在每个表单中包含令牌，该辅助函数渲染一个包含令牌的隐藏输入字段。

edge
<form method="POST" action="/posts">
  {{-- 渲染带有 CSRF 令牌的隐藏输入 --}}
  {{ csrfField() }}

  <input type="text" name="title" placeholder="Post title">
  <textarea name="content" placeholder="Write your post..."></textarea>
  <button type="submit">Create Post</button>
</form>

该辅助函数生成一个隐藏输入字段，Shield 的中间件在提交时验证它。

html
<form method="POST" action="/posts">
  <input type="hidden" name="_csrf" value="Q9ghWSf0-3FD9eCiu5YxvKaxLEZ6F_K4DL8o"/>

  <input type="text" name="title" placeholder="Post title">
  <textarea name="content" placeholder="Write your post..."></textarea>
  <button type="submit">Create Post</button>
</form>

处理 CSRF 错误 ​

当令牌缺失或无效时，Shield 抛出 E_BAD_CSRF_TOKEN 异常。默认情况下，AdonisJS 将用户重定向回表单并带有错误闪存消息。你可以在模板中使用 @error 标签显示此消息。

edge
@error('E_BAD_CSRF_TOKEN')
  <p class="error">{{ $message }}</p>
@end

<form method="POST" action="/posts">
  {{ csrfField() }}
  {{-- 表单字段 --}}
</form>

对于自定义错误处理，你可以在全局异常处理器中捕获该异常。当你想要渲染自定义错误页面或返回特定响应格式时，这很有用。

ts
import app from '@adonisjs/core/services/app'
import { errors } from '@adonisjs/shield'
import { HttpContext, ExceptionHandler } from '@adonisjs/core/http'

export default class HttpExceptionHandler extends ExceptionHandler {
  async handle(error: unknown, ctx: HttpContext) {
    /**
     * 检查错误是否为 CSRF 令牌错误，并返回
     * 自定义响应而不是默认重定向。
     */
    if (error instanceof errors.E_BAD_CSRF_TOKEN) {
      return ctx.response
        .status(error.status)
        .send('Your session has expired. Please refresh the page and try again.')
    }

    return super.handle(error, ctx)
  }
}

为 Ajax 请求启用 CSRF 令牌 ​

单页应用和交互式界面通常通过 JavaScript 而不是传统表单提交来提交表单。对于这些情况，Shield 可以在 cookie 中暴露 CSRF 令牌，供你的前端代码读取。

当启用 enableXsrfCookie 时，Shield 将令牌存储在名为 XSRF-TOKEN 的加密 cookie 中。Axios 等前端库会自动读取此 cookie，并将其作为 X-XSRF-TOKEN 头随每个请求包含。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csrf: {
    enabled: true,
    exceptRoutes: [],
    enableXsrfCookie: true, 
    methods: ['POST', 'PUT', 'PATCH', 'DELETE'],
  },
})

export default shieldConfig

TIP

仅当你的应用发起 Ajax 请求时才启用 enableXsrfCookie。对于使用完整页面提交的传统服务端渲染表单，隐藏输入字段就足够了，而且更安全。

从 CSRF 保护中豁免路由 ​

接收 webhook 或来自外部服务请求的 API 端点无法包含 CSRF 令牌。你可以使用 exceptRoutes 选项豁免特定路由。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csrf: {
    enabled: true,
    exceptRoutes: [
      '/api/webhooks/*',
      '/api/payments/callback',
    ],
    enableXsrfCookie: false,
    methods: ['POST', 'PUT', 'PATCH', 'DELETE'],
  },
})

export default shieldConfig

对于动态豁免逻辑，传递一个接收 HTTP 上下文并返回布尔值的函数。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csrf: {
    enabled: true,
    exceptRoutes: (ctx) => {
      /**
       * 豁免所有以 /api/ 开头的路由，因为这些路由
       * 由具有自己身份认证机制的外部服务消费。
       */
      return ctx.request.url().startsWith('/api/')
    },
    enableXsrfCookie: false,
    methods: ['POST', 'PUT', 'PATCH', 'DELETE'],
  },
})

export default shieldConfig

CSRF 配置参考 ​

选项类型描述
enabledboolean打开或关闭 CSRF 保护。
exceptRoutesstring[] 或 function从 CSRF 保护中豁免的路由。接受路由模式或接收 HttpContext 的函数。
enableXsrfCookieboolean当为 true 时，将 CSRF 令牌存储在 XSRF-TOKEN cookie 中供 Ajax 请求使用。
methodsstring[]需要 CSRF 令牌验证的 HTTP 方法。默认为 POST、PUT、PATCH、DELETE。
cookieOptionsobjectXSRF-TOKEN cookie 的配置。参阅 cookie 配置。

CSP（内容安全策略） ​

XSS（跨站脚本）攻击将恶意脚本注入你的页面。攻击者可能利用未清理输入的评论表单，注入窃取用户 cookie 或将其重定向到钓鱼站点的 JavaScript。即使有适当的输入清理，XSS 漏洞也可能漏网。

CSP 通过告诉浏览器哪些内容源是可信的来提供第二道防线。当你定义 CSP 策略时，浏览器将阻止任何与允许源不匹配的脚本、样式或其他资源。即使攻击者设法注入了一个 script 标签，浏览器也会拒绝执行它，因为它不是从可信源加载的。

启用 CSP ​

CSP 默认禁用，因为策略必须根据你的应用需求定制。启用它并在配置文件中定义你的指令。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csp: {
    enabled: true,
    directives: {
      defaultSrc: [`'self'`],
      scriptSrc: [`'self'`, 'https://cdnjs.cloudflare.com'],
      styleSrc: [`'self'`, 'https://fonts.googleapis.com'],
      fontSrc: [`'self'`, 'https://fonts.gstatic.com'],
      imgSrc: [`'self'`, 'data:', 'https://images.example.com'],
    },
    reportOnly: false,
  },
})

export default shieldConfig

defaultSrc 指令充当任何你未显式配置的资源类型的回退。'self' 关键字允许来自你自己域的资源。每个指令控制特定的资源类型：scriptSrc 用于 JavaScript，styleSrc 用于 CSS，fontSrc 用于字体，依此类推。

你可以在 content-security-policy.com 找到可用指令的完整列表。

为内联脚本和样式使用 nonce ​

内联脚本和样式在 CSP 下默认被阻止，因为它们是常见的 XSS 攻击向量。但是，你可能出于合法目的需要内联代码。Nonce（一次性随机数）允许特定的内联块，同时保持整体策略严格。

将 @nonce 关键字添加到你的指令中，然后使用 Edge 模板中可用的 cspNonce 变量，在内联 script 和 style 标签上包含 nonce 属性。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csp: {
    enabled: true,
    directives: {
      defaultSrc: [`'self'`],
      scriptSrc: [`'self'`, '@nonce'],
      styleSrc: [`'self'`, '@nonce'],
    },
    reportOnly: false,
  },
})

export default shieldConfig
edge
<script nonce="{{ cspNonce }}">
  // 此内联脚本将执行，因为它具有有效的 nonce
  console.log('Application initialized')
</script>

<style nonce="{{ cspNonce }}">
  /* 此内联样式将应用，因为它具有有效的 nonce */
  .highlight { background: yellow; }
</style>

Shield 为每个请求生成唯一的 nonce。攻击者无法预测此值，因此即使他们注入了 script 标签，它也不会具有有效的 nonce，浏览器将阻止它。

为 Vite 配置 CSP ​

使用 Vite 进行资源打包时，你需要在开发期间允许来自 Vite 开发服务器的资源。Shield 为此提供了特殊关键字。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csp: {
    enabled: true,
    directives: {
      defaultSrc: [`'self'`, '@viteDevUrl'],
      connectSrc: [`'self'`, '@viteHmrUrl'],
      scriptSrc: [`'self'`, '@nonce'],
      styleSrc: [`'self'`, '@nonce'],
    },
    reportOnly: false,
  },
})

export default shieldConfig

@viteDevUrl 关键字解析为 Vite 开发服务器 URL，而 @viteHmrUrl 允许热模块替换的 WebSocket 连接。

如果你将打包资源部署到 CDN，请将 @viteDevUrl 替换为 @viteUrl。此关键字允许来自开发服务器和生产 CDN 的资源。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csp: {
    enabled: true,
    directives: {
      defaultSrc: [`'self'`, '@viteUrl'], 
      connectSrc: [`'self'`, '@viteHmrUrl'],
      scriptSrc: [`'self'`, '@nonce'],
      styleSrc: [`'self'`, '@nonce'],
    },
    reportOnly: false,
  },
})

export default shieldConfig

WARNING

Vite 目前不支持向其开发期间注入 DOM 的 style 标签添加 nonce 属性。这是 Vite 团队正在解决的已知限制。在解决之前，你可能需要在开发期间对 styleSrc 使用 'unsafe-inline'，然后在生产环境中切换到基于 nonce 的策略。

使用仅报告模式测试策略 ​

配置错误的 CSP 可能通过阻止合法资源来破坏你的应用。使用 reportOnly 模式测试你的策略而不强制执行。在此模式下，浏览器报告违规但不阻止资源。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  csp: {
    enabled: true,
    directives: {
      defaultSrc: [`'self'`],
      reportUri: ['/csp-report'],
    },
    reportOnly: true,
  },
})

export default shieldConfig

创建一个端点来收集违规报告。这有助于你在启用强制执行之前识别忘记加入白名单的资源。

ts
import router from '@adonisjs/core/services/router'

router.post('/csp-report', async ({ request, logger }) => {
  const report = request.input('csp-report')
  logger.warn({ report }, 'CSP violation detected')
})

一旦你验证了策略没有阻止合法资源，将 reportOnly 设置为 false 以启用强制执行。

CSP 配置参考 ​

选项类型描述
enabledboolean打开或关闭 CSP。
directivesobject定义每种资源类型允许源的 CSP 指令。
reportOnlyboolean当为 true 时，报告违规但不阻止。用于测试策略。

HSTS（HTTP 严格传输安全） ​

当用户输入你的域而不带 https:// 时，浏览器首先通过不安全的 HTTP 连接，然后重定向到 HTTPS。这个短暂的窗口允许攻击者通过中间人攻击拦截初始请求，可能降级连接或窃取敏感数据。

HSTS 告诉浏览器始终为你的域使用 HTTPS，即使用户输入 http:// 或点击普通 HTTP 链接。收到 HSTS 头后，浏览器会在指定持续时间内自动将所有请求升级为 HTTPS，消除不安全的重定向窗口。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  hsts: {
    enabled: true,
    maxAge: '180 days',
    includeSubDomains: true,
  },
})

export default shieldConfig

maxAge 选项告诉浏览器记住仅 HTTPS 策略的时长。includeSubDomains 选项将这一保护扩展到所有子域，防止攻击者利用不安全的子域来危害你的主域。

WARNING

只有在确认 HTTPS 在整个域和所有子域上正常工作后才启用 HSTS。一旦浏览器缓存了 HSTS 策略，它们将在 maxAge 持续时间内拒绝通过 HTTP 连接。如果你的 HTTPS 配置出现问题，用户将无法访问你的站点，直到你修复它或缓存的策略过期。

在测试期间从较短的 maxAge（如 1 day）开始，一旦你对 HTTPS 设置有信心，就增加到 180 days 或更长。

HSTS 配置参考 ​

选项类型描述
enabledboolean打开或关闭 HSTS。
maxAgenumber 或 string浏览器应记住仅 HTTPS 策略的时长。接受数字形式的秒数或像 '180 days' 这样的时间表达式。
includeSubDomainsboolean当为 true 时，将仅 HTTPS 策略应用于所有子域。

X-Frame-Options（点击劫持保护） ​

点击劫持攻击将你的站点嵌入恶意页面上的不可见 iframe 中。攻击者覆盖欺骗性内容，诱骗用户点击隐藏站点上的按钮。用户可能认为他们点击的是“播放视频”按钮，但实际上点击的是你应用上的“删除账户”。

X-Frame-Options 头防止你的页面被嵌入其他站点的框架中。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  xFrame: {
    enabled: true,
    action: 'DENY',
  },
})

export default shieldConfig

DENY 操作阻止所有框架嵌入。如果你需要在你自己的域上嵌入站点框架（例如管理面板预览），改用 SAMEORIGIN。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  xFrame: {
    enabled: true,
    action: 'SAMEORIGIN',
  },
})

export default shieldConfig

要允许特定外部域嵌入你的内容框架，使用 ALLOW-FROM 和该域。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  xFrame: {
    enabled: true,
    action: 'ALLOW-FROM',
    domain: 'https://trusted-partner.com',
  },
})

export default shieldConfig

TIP

如果你已配置 CSP，可以使用 frame-ancestors 指令代替 X-Frame-Options。CSP 指令提供更多灵活性，包括支持多个域。使用 frame-ancestors 时，你可以禁用 xFrame 防护以避免冗余头。

X-Frame 配置参考 ​

选项类型描述
enabledboolean打开或关闭 X-Frame 保护。
actionstring框架策略：'DENY'、'SAMEORIGIN' 或 'ALLOW-FROM'。
domainstring当 action 为 'ALLOW-FROM' 时必需。允许嵌入你内容的域。

内容类型嗅探保护 ​

浏览器在服务器未正确指定内容类型时尝试通过猜测内容类型来提供帮助。如果你的服务器意外地以错误的内容类型提供用户上传的文件，浏览器可能“嗅探”内容并将其作为脚本执行。攻击者可以上传一个看起来像图片但包含 JavaScript 的文件，浏览器可能会执行它。

X-Content-Type-Options: nosniff 头告诉浏览器信任 Content-Type 头，永不猜测。这防止内容类型混淆攻击。

ts
import { defineConfig } from '@adonisjs/shield'

const shieldConfig = defineConfig({
  contentTypeSniffing: {
    enabled: true,
  },
})

export default shieldConfig

此防护没有额外的配置选项。启用时，Shield 向所有响应添加 X-Content-Type-Options: nosniff 头。
