队列 ​

WARNING

@adonisjs/queue 包目前处于实验阶段。在达到稳定版本之前，其 API 可能会在次要版本之间发生变化。请在 package.json 中固定包版本，以避免更新期间出现意外的破坏性更改。

本指南涵盖 AdonisJS 中使用队列进行后台任务处理。你将了解到如何：

  • 使用 Redis 或数据库后端安装和配置队列系统
  • 创建任务并将其分发以进行后台处理
  • 通过分发时去重防止重复任务
  • 延迟任务、设置优先级和批量分发
  • 配置指数、线性或固定退避的重试策略
  • 使用 cron 表达式或间隔调度循环任务
  • 启动工作进程从队列处理任务
  • 使用 fake 适配器测试任务分发

概述 ​

Web 应用经常需要执行太慢或资源密集而无法在 HTTP 请求期间运行的任务。发送电子邮件、生成报告、处理支付或调整图片大小都是应在后台发生的工作示例，以便你的用户获得即时响应。

@adonisjs/queue 包为 AdonisJS 提供任务队列系统，构建在 @boringnode/queue 之上。你将任务定义为带有类型化负载的类，从应用代码分发它们，并运行单独的工作进程来接收和执行这些任务。

该包支持多种后端。Redis 适配器推荐用于生产环境，提供原子操作和高吞吐量。Database 适配器通过 Lucid 使用你现有的 SQL 数据库（PostgreSQL、MySQL 或 SQLite）。Sync 适配器也可用于开发和测试，无需单独的工作进程即可立即执行任务。

安装 ​

使用以下命令安装和配置该包：

sh
node ace add @adonisjs/queue
查看 add 命令执行的步骤

  1. 使用检测到的包管理器安装 @adonisjs/queue 包。

  2. 在 adonisrc.ts 文件中注册以下服务提供者、命令和预加载文件。

    ts
    {
  commands: [
    // ...其他命令
    () => import('@adonisjs/queue/commands')
  ],
  providers: [
    // ...其他提供者
    () => import('@adonisjs/queue/queue_provider')
  ],
  preloads: [
    // ...其他预加载
    () => import('#start/scheduler')
  ]
}

  3. 创建 config/queue.ts 文件。

  4. 创建 start/scheduler.ts 预加载文件以定义调度任务。

  5. 定义 QUEUE_DRIVER 环境变量及其验证。

  6. 如果你选择数据库驱动，创建迁移以设置队列表。

配置 ​

配置文件位于 config/queue.ts。它定义你的适配器、要使用的默认适配器、工作进程设置以及任务文件的位置。

另请参阅：配置存根

ts
import env from '#start/env'
import { defineConfig, drivers } from '@adonisjs/queue'

export default defineConfig({
  default: env.get('QUEUE_DRIVER', 'redis'),

  adapters: {
    redis: drivers.redis({
      connectionName: 'main',
    }),
    sync: drivers.sync(),
  },

  worker: {
    concurrency: 5,
    idleDelay: '2s',
  },

  locations: ['./app/jobs/**/*.{ts,js}'],
})

default

类型：string

分发任务时默认使用的适配器名称。此值通常通过 QUEUE_DRIVER 环境变量设置。

adapters

类型：Record<string, AdapterFactory>

命名适配器的记录。每个适配器使用 drivers 辅助函数之一创建：drivers.redis()、drivers.database() 或 drivers.sync()。你可以配置多个适配器并在运行时切换它们。

worker

类型：WorkerConfig

工作进程的配置。所有可用选项请参阅工作进程配置。

locations

类型：string[]

指向任务文件的 glob 模式数组。队列系统使用这些模式自动发现和注册任务类。

ts
{
  locations: ['./app/jobs/**/*.{ts,js}'],
}

retry

类型：RetryConfig

应用于所有任务的全局重试配置，除非在队列或任务级别覆盖。详情请参阅重试和退避。

queues

类型：Record<string, QueueConfig>

按队列配置，允许你为特定队列设置不同的重试策略或默认任务选项。

ts
{
  queues: {
    emails: {
      retry: {
        maxRetries: 5,
      },
    },
  },
}

defaultJobOptions

类型：JobOptions

应用于所有任务的默认选项。单个任务可以在其 static options 属性中覆盖这些选项。

适配器配置 ​

Redis ​

Redis 适配器使用你的 @adonisjs/redis 连接。由于其原子操作和高吞吐量，它是生产环境的推荐选择。

ts
import { defineConfig, drivers } from '@adonisjs/queue'

export default defineConfig({
  default: 'redis',
  adapters: {
    redis: drivers.redis({
      // 使用 config/redis.ts 中的 'main' 连接
      connectionName: 'main',
    }),
  },
  // ...
})

你必须安装并配置 @adonisjs/redis 才能使此适配器工作。

Database ​

Database 适配器使用你的 @adonisjs/lucid 连接，支持 PostgreSQL、MySQL 或 SQLite。当你想要避免将 Redis 添加到基础设施时，这是一个好的选择。

ts
import { defineConfig, drivers } from '@adonisjs/queue'

export default defineConfig({
  default: 'database',
  adapters: {
    database: drivers.database({
      connectionName: 'primary',
    }),
  },
  // ...
})

在安装期间选择数据库驱动时，会自动创建迁移。如果你需要手动创建表，使用 QueueSchemaService：

ts
import { BaseSchema } from '@adonisjs/lucid/schema'
import { QueueSchemaService } from '@adonisjs/queue'

export default class extends BaseSchema {
  async up() {
    const schemaService = new QueueSchemaService(this.db.getWriteClient())

    await schemaService.createJobsTable()
    await schemaService.createSchedulesTable()
  }

  async down() {
    const schemaService = new QueueSchemaService(this.db.getWriteClient())

    await schemaService.dropSchedulesTable()
    await schemaService.dropJobsTable()
  }
}

你必须安装并配置 @adonisjs/lucid 才能使此适配器工作。

Sync ​

Sync 适配器在同一进程中立即执行任务，无需单独的工作进程。这对于开发和测试很有用，当你想要立即看到任务结果时。

ts
import { defineConfig, drivers } from '@adonisjs/queue'

export default defineConfig({
  default: 'sync',
  adapters: {
    sync: drivers.sync(),
  },
  // ...
})

TIP

你可以使用 QUEUE_DRIVER 环境变量按环境切换适配器。在生产环境中使用 redis 或 database，在开发环境中使用 sync。

创建任务 ​

任务是一个封装要在后台执行的工作单元的类。每个任务继承 Job 基类并带有类型化负载。

使用 make:job Ace 命令生成新任务：

sh
node ace make:job process_payment

这会在 app/jobs/process_payment.ts 创建任务类：

ts
import { Job } from '@adonisjs/queue'
import type { JobOptions } from '@adonisjs/queue/types'

interface ProcessPaymentPayload {
  orderId: number
  amount: number
  currency: string
}

export default class ProcessPayment extends Job<ProcessPaymentPayload> {
  static options: JobOptions = {
    queue: 'default',
    maxRetries: 3,
  }

  async execute() {
    const { orderId, amount, currency } = this.payload

    // 使用你的支付网关处理支付
    console.log(`Processing payment of ${amount} ${currency} for order ${orderId}`)
  }

  async failed(error: Error) {
    console.error(`Payment processing failed for order ${this.payload.orderId}:`, error.message)
  }
}

Job 类提供两个要实现的方法：

  • execute()（必需）：包含主要任务逻辑。此处抛出的任何错误都会触发重试机制。
  • failed(error)（可选）：当任务在所有重试耗尽后永久失败时调用。用于清理、日志记录或发送通知。

任务选项 ​

通过设置 static options 属性为你的任务配置默认行为。

queue

类型：string

将此任务分发到的队列。默认为 'default'。

maxRetries

类型：number

任务永久失败之前的最大重试尝试次数。默认为 0，除非在全局或队列级别配置。

priority

类型：number

任务优先级从 1 到 10。数字越小越先处理。默认为 5。

timeout

类型：Duration

任务超时之前的最大执行时间。接受毫秒数或像 '30s' 或 '5m' 这样的持续时间字符串。默认无超时。

failOnTimeout

类型：boolean

超时时是否将任务标记为永久失败。当为 false 时，超时的任务遵循正常重试策略。默认为 false。

retry

类型：RetryConfig

特定于此任务的重试配置，覆盖全局和队列级别设置。参阅重试和退避。

removeOnComplete

类型：JobRetention

控制已完成任务是否保留在历史记录中。设置为 true 立即移除（默认），false 永久保留，或带有 age 和/或 count 约束的对象。

ts
{ removeOnComplete: { age: '7d', count: 1000 } }

removeOnFail

类型：JobRetention

控制已失败任务是否保留在历史记录中。格式与 removeOnComplete 相同。

任务上下文 ​

执行期间，你可以通过 this.context 访问当前任务的元数据：

ts
export default class ProcessPayment extends Job<ProcessPaymentPayload> {
  async execute() {
    // 访问任务元数据
    console.log(`Job ID: ${this.context.jobId}`)
    console.log(`Attempt: ${this.context.attempt}`)
    console.log(`Queue: ${this.context.queue}`)
    console.log(`Priority: ${this.context.priority}`)
  }
}

处理超时 ​

对于长时间运行的任务，你可以检查 this.signal 以检测何时达到超时并优雅地处理它：

ts
import { Job } from '@adonisjs/queue'
import type { JobOptions } from '@adonisjs/queue/types'

interface GenerateReportPayload {
  reportId: number
  rows: number[]
}

export default class GenerateReport extends Job<GenerateReportPayload> {
  static options: JobOptions = {
    timeout: '5m',
    failOnTimeout: false, // 重试而不是永久失败
  }

  async execute() {
    for (const rowId of this.payload.rows) {
      // 在处理每一行之前检查任务是否已超时
      if (this.signal?.aborted) {
        throw new Error('Job timed out during report generation')
      }

      await this.processRow(rowId)
    }
  }

  private async processRow(rowId: number) {
    // 处理单个行
  }
}

依赖注入 ​

任务通过 AdonisJS IoC 容器实例化，因此你可以使用构造函数注入来访问服务：

ts
import { inject } from '@adonisjs/core'
import { Job } from '@adonisjs/queue'
import type { JobOptions } from '@adonisjs/queue/types'
import PaymentService from '#services/payment_service'

interface ProcessPaymentPayload {
  orderId: number
  amount: number
  currency: string
}

@inject()
export default class ProcessPayment extends Job<ProcessPaymentPayload> {
  static options: JobOptions = {
    queue: 'payments',
    maxRetries: 3,
  }

  constructor(private paymentService: PaymentService) {
    super()
  }

  async execute() {
    await this.paymentService.charge(
      this.payload.orderId,
      this.payload.amount,
      this.payload.currency
    )
  }
}

分发任务 ​

使用静态 dispatch 方法从应用中的任何地方分发任务。任务负载是类型安全的，与任务类上定义的泛型参数匹配。

ts
import ProcessPayment from '#jobs/process_payment'

export default class OrdersController {
  async store({ request, response }: HttpContext) {
    const order = await Order.create(request.body())

    // 分发任务以进行后台处理
    await ProcessPayment.dispatch({
      orderId: order.id,
      amount: order.total,
      currency: 'USD',
    })

    return response.created(order)
  }
}

从 Ace 命令分发任务 ​

当你的应用为 HTTP 请求启动时，locations 配置中的任务文件会自动加载。queue:work 命令在启动工作进程之前也会加载它们。

自定义 Ace 命令不同：在控制台启动生命周期中不会自动发现任务。如果你的命令分发任务且你在本地或测试中使用 sync 适配器，在分发之前加载配置的任务位置。

ts
import { BaseCommand } from '@adonisjs/core/ace'
import ImportOrders from '#jobs/import_orders'

export default class ImportOrdersCommand extends BaseCommand {
  static commandName = 'orders:import'

  static options = {
    startApp: true,
  }

  async run() {
    const queue = await this.app.container.make('queue.manager')

    await queue.loadJobs()

    await ImportOrders.dispatch({
      source: 'warehouse',
    })
  }
}

如果你的命令仅向 Redis 或数据库分发任务，导入任务类就足以将其入队。调用 queue.loadJobs() 使同一命令与 sync 适配器兼容，后者在当前进程中立即执行任务。

分发选项 ​

dispatch 方法返回一个流畅构建器，让你在将任务发送到队列之前自定义任务行为：

ts
// 分发到特定队列并设置高优先级
await ProcessPayment.dispatch({
  orderId: order.id,
  amount: order.total,
  currency: 'USD',
})
  .toQueue('payments')
  .priority(1)

.toQueue(name)（类型：string）

将任务发送到特定队列而不是默认队列。

ts
await ProcessPayment.dispatch(payload).toQueue('payments')

.priority(level)（类型：number）

设置任务优先级。数字越小越先处理（1 = 最高优先级，10 = 最低）。

ts
await ProcessPayment.dispatch(payload).priority(1)

.in(delay)（类型：Duration）

将任务执行延迟指定时长。接受毫秒数或像 '5m'、'1h'、'7d' 这样的字符串。

ts
// 24 小时后发送提醒
await SendReminder.dispatch(payload).in('24h')

.group(groupId)（类型：string）

分配组标识符以组织相关任务。对于跟踪批量操作很有用。

ts
await GenerateReport.dispatch(payload).group('monthly-reports-2025')

.with(adapter)（类型：string）

为此任务使用特定适配器而不是默认适配器。

ts
await ProcessPayment.dispatch(payload).with('redis')

去重任务 ​

任务去重防止多个单任务分发将相同的工作入队。当 HTTP 重试、webhook 重试或重复按钮点击可能多次分发同一后台任务时，这很有用。

dedup 方法接受用户定义的 id。在内部，队列会为其添加任务名称前缀，因此两个不同的任务类可以使用相同的 id 而不会冲突。

ts
import type { HttpContext } from '@adonisjs/core/http'
import Order from '#models/order'
import ProcessPayment from '#jobs/process_payment'

export default class OrdersController {
  async retryPayment({ params, response }: HttpContext) {
    const order = await Order.findOrFail(params.id)

    const result = await ProcessPayment.dispatch({
      orderId: order.id,
      amount: order.total,
      currency: order.currency,
    })
      .toQueue('payments')
      .dedup({ id: `order:${order.id}`, ttl: '10m' })

    return response.accepted({
      jobId: result.jobId,
      deduped: result.deduped,
    })
  }
}

当使用 .dedup() 时，分发结果包含一个 deduped 结果。当你的控制器或服务需要对被跳过或替换的分发做出不同反应时，使用此值。

结果含义
added插入了新任务
skipped重复任务已存在，新分发被忽略
replaced待处理或延迟的重复任务保留了其任务 ID，但接收了最新负载
extended重复任务被跳过，其去重窗口被刷新

去重支持以下分发模式：

方法调用行为
.dedup({ id })当具有相同键的现有任务仍然存在时跳过重复
.dedup({ id, ttl })在时间窗口内跳过重复
.dedup({ id, ttl, extend: true })跳过重复并在每次重复时刷新时间窗口
.dedup({ id, ttl, replace: true })替换现有待处理或延迟任务的负载
.dedup({ id, ttl, extend: true, replace: true })通过替换负载和刷新时间窗口来防抖分发

extend 和 replace 选项需要正数 ttl。使用 replace 时，仅更新任务负载。现有任务保留其队列、优先级、延迟和组 ID。活动任务和保留的已完成或已失败任务会被跳过而不是被修改。

WARNING

去重仅由 Redis 和 Database 适配器应用于单任务分发。Sync 适配器内联运行每次分发，批量分发或调度任务不应用去重。

当防止重复很重要时，使用 Redis 或数据库。对于批量或调度工作流，在应用逻辑、数据库约束或专用锁中强制唯一性。

用户提供的 id 必须为 400 个字符或更少。构建为 <jobName>::<id> 的最终键必须为 510 个字符或更少。

批量分发 ​

当你需要分发许多相同类型的任务时，使用 dispatchMany 以获得更好的性能。它在底层使用批量操作（Redis 管道或 SQL 批量插入）。

ts
import SendNewsletter from '#jobs/send_newsletter'

export default class NewsletterService {
  async sendToAllSubscribers(subscribers: { email: string }[]) {
    const payloads = subscribers.map((subscriber) => ({
      email: subscriber.email,
      subject: 'Monthly Newsletter',
    }))

    const { jobIds } = await SendNewsletter.dispatchMany(payloads)
      .toQueue('emails')
      .group('newsletter-march-2025')

    console.log(`Dispatched ${jobIds.length} newsletter jobs`)
  }
}

重试和退避 ​

当任务抛出错误时，队列系统根据配置的重试策略自动重试它。你可以在三个级别配置重试，更具体的设置优先：任务 > 队列 > 全局。

退避策略 ​

退避策略控制重试尝试之间的延迟。该包提供四种内置策略：

ts
import { defineConfig, drivers } from '@adonisjs/queue'
import { exponentialBackoff } from '@adonisjs/queue'

export default defineConfig({
  default: 'redis',
  adapters: {
    redis: drivers.redis({ connectionName: 'main' }),
  },
  retry: {
    maxRetries: 3,
    backoff: exponentialBackoff(),
  },
  // ...
})

指数退避每次尝试将延迟翻倍：1s、2s、4s、8s，依此类推。这是大多数用例的推荐策略，因为它防止压垮失败的服务。

ts
import { exponentialBackoff } from '@adonisjs/queue'

// 默认：1s 基础，5m 最大，2x 乘数，启用抖动
exponentialBackoff()

// 自定义
exponentialBackoff({ baseDelay: '500ms', maxDelay: '1m' })

线性退避每次尝试按基础量增加延迟：5s、10s、15s、20s，依此类推。

ts
import { linearBackoff } from '@adonisjs/queue'

// 默认：5s 基础，2m 最大
linearBackoff()

// 自定义
linearBackoff({ baseDelay: '10s', maxDelay: '5m' })

固定退避每次重试使用相同的延迟：10s、10s、10s，依此类推。

ts
import { fixedBackoff } from '@adonisjs/queue'

// 默认：10s
fixedBackoff()

// 自定义
fixedBackoff('30s')

自定义退避让你完全控制策略配置：

ts
import { customBackoff } from '@adonisjs/queue'

customBackoff({
  strategy: 'exponential',
  baseDelay: '100ms',
  maxDelay: '30s',
  multiplier: 3,
  jitter: false,
})

TIP

在指数和线性策略上启用 jitter 以为重试延迟添加随机性。这防止多个失败的任务在完全相同的时间重试，这可能使下游服务过载（一种称为"惊群效应"的模式）。

按任务重试 ​

你可以为特定任务覆盖重试配置：

ts
import { Job } from '@adonisjs/queue'
import { exponentialBackoff } from '@adonisjs/queue'
import type { JobOptions } from '@adonisjs/queue/types'

export default class ProcessPayment extends Job<ProcessPaymentPayload> {

调度任务 ​

调度任务按定义的间隔或 cron 表达式自动运行。在 start/scheduler.ts 预加载文件中定义你的调度。

Cron 调度 ​

使用 cron 表达式进行精确调度：

ts
import CleanupExpiredSessions from '#jobs/cleanup_expired_sessions'
import GenerateWeeklyReport from '#jobs/generate_weekly_report'

// 每晚午夜运行
await CleanupExpiredSessions.schedule({ retentionDays: 30 })
  .cron('0 0 * * *')
  .timezone('Europe/Paris')

// 每周一上午 9 点运行
await GenerateWeeklyReport.schedule({ type: 'weekly' })
  .cron('0 9 * * MON')
  .timezone('America/New_York')

间隔调度 ​

对于更简单的用例，以固定间隔调度任务：

ts
import SyncInventory from '#jobs/sync_inventory'

// 每 5 分钟运行
await SyncInventory.schedule({ source: 'warehouse-api' })
  .every('5m')

调度选项 ​

调度构建器支持以下选项：

.cron(expression)（类型：string）

定义任务何时运行的 cron 表达式。与 .every() 互斥。

.every(interval)（类型：Duration）

运行之间的持续时间间隔。与 .cron() 互斥。

.id(scheduleId)（类型：string）

调度的自定义标识符。默认为任务类名称。如果具有此 ID 的调度已存在，它将被更新。

.timezone(tz)（类型：string）

用于求值 cron 表达式的 IANA 时区。默认为 'UTC'。

.from(date)（类型：Date）

起始边界。在此日期之前不会分发任何任务。

.to(date)（类型：Date）

结束边界。在此日期之后不会分发任何任务。

.between(from, to)（类型：Date, Date）

同时设置 .from() 和 .to() 的简写。

.limit(maxRuns)（类型：number）

调度将运行的最大次数。

管理调度 ​

你可以使用 Schedule 类以编程方式管理调度：

ts
import { Schedule } from '@adonisjs/queue'

export default class AdminController {
  async listSchedules() {
    // 列出所有调度
    const schedules = await Schedule.list()

    // 仅列出活动调度
    const active = await Schedule.list({ status: 'active' })

    return schedules
  }

  async pauseSchedule({ params }: HttpContext) {
    const schedule = await Schedule.find(params.id)

    if (schedule) {
      await schedule.pause()
    }
  }

  async resumeSchedule({ params }: HttpContext) {
    const schedule = await Schedule.find(params.id)

    if (schedule) {
      await schedule.resume()
    }
  }

  async triggerSchedule({ params }: HttpContext) {
    const schedule = await Schedule.find(params.id)

    if (schedule) {
      // 立即分发调度任务
      await schedule.trigger()
    }
  }

  async deleteSchedule({ params }: HttpContext) {
    const schedule = await Schedule.find(params.id)

    if (schedule) {
      await schedule.delete()
    }
  }
}

运行工作进程 ​

在你启动工作进程之前，任务不会被处理。工作进程是一个长期运行的进程，轮询队列以获取可用任务并执行它们。

工作进程还为活动任务发送心跳。这些心跳在处理程序仍在运行时续期任务所有权时间戳，因此健康的长运行任务不会仅仅因为运行时间超过 stalledThreshold 而被恢复为停滞。工作进程只能续期它仍然拥有的任务，因此迟到的���跳无法延长已被另一个工作进程恢复的任务。

使用 queue:work Ace 命令启动工作进程：

sh
node ace queue:work

工作进程选项 ​

sh
# 处理特定队列
node ace queue:work --queue=payments,emails

# 设置并发数（同时处理的任务数）
node ace queue:work --concurrency=10

WARNING

你必须将工作进程作为单独进程与 Web 服务器一起启动。从你的应用分发的任务在工作进程运行之前不会被处理。

在生产环境中，使用像 PM2 这样的进程管理器或容器编排器来保持工作进程运行并在失败时重启它。

工作进程配置 ​

在你的 config/queue.ts 文件中配置工作进程行为：

ts
export default defineConfig({
  // ...
  worker: {
    concurrency: 5,
    idleDelay: '2s',
    stalledThreshold: '30s',
    stalledInterval: '30s',
    maxStalledCount: 1,
    gracefulShutdown: true,
  },
})

concurrency（类型：number）

同时处理的最大任务数。默认为 1。

idleDelay（类型：Duration）

没有可用任务时工作进程再次轮询之前的等待时长。默认为 '2s'。

timeout（类型：Duration）

任何任务的全局最大执行时间。可以通过 JobOptions.timeout 按任务覆盖。默认无超时。

stalledThreshold（类型：Duration）

任务在被视为停滞之前可以多长时间没有心跳。这是崩溃检测窗口，不是最大任务运行时间。当你想要限制任务可以运行多长时间时，使用 timeout 或 JobOptions.timeout。默认为 '30s'。

stalledInterval（类型：Duration）

工作进程检查停滞任务的频率。默认为 '30s'。

maxStalledCount（类型：number）

停滞任务在被永久失败之前可以被恢复的最大次数。默认为 1。

gracefulShutdown（类型：boolean）

当为 true 时，工作进程在收到 SIGINT/SIGTERM 信号时先完成正在运行的任务再停止。默认为 true。

测试 ​

该包提供一个 fake 适配器，在内存中记录已分发的任务并暴露断言辅助函数。这让你验证应用分发正确的任务而不实际处理它们。

伪造队列 ​

使用 QueueManager.fake() 将所有适配器替换为 fake 适配器，使用 QueueManager.restore() 恢复：

ts
import { test } from '@japa/runner'
import { QueueManager } from '@adonisjs/queue'
import ProcessPayment from '#jobs/process_payment'

test.group('Orders', (group) => {
  group.each.teardown(() => {
    QueueManager.restore()
  })

  test('dispatches a payment job when creating an order', async ({ client }) => {
    const fake = QueueManager.fake()

    const response = await client.post('/orders').json({
      product_id: 1,
      quantity: 2,
    })

    response.assertStatus(201)

    // 断言任务已分发
    fake.assertPushed(ProcessPayment)

    // 使用负载匹配进行断言
    fake.assertPushed(ProcessPayment, {
      payload: { orderId: 1, amount: 100, currency: 'USD' },
    })
  })

  test('does not dispatch a payment job for free orders', async ({ client }) => {
    const fake = QueueManager.fake()

    await client.post('/orders').json({
      product_id: 1,
      quantity: 0,
    })

    fake.assertNotPushed(ProcessPayment)
  })
})

断言方法 ​

Fake 适配器提供以下断言方法：

assertPushed(job, query?)（类型：void）

断言任务已分发。可选地按队列、负载或延迟过滤。

ts
fake.assertPushed(ProcessPayment)
fake.assertPushed(ProcessPayment, { queue: 'payments' })
fake.assertPushed(ProcessPayment, {
  payload: { orderId: 1 },
})

assertNotPushed(job, query?)（类型：void）

断言任务未分发。

ts
fake.assertNotPushed(SendEmail)

assertPushedCount(count, options?)（类型：void）

断言已分发任务的总数，可选地按队列过滤。

ts
fake.assertPushedCount(3)
fake.assertPushedCount(2, { queue: 'emails' })

assertNothingPushed()（类型：void）

断言完全没有分发任何任务。

ts
fake.assertNothingPushed()

ts
import { test } from '@japa/runner'
