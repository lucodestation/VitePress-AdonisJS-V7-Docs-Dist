依赖注入与 IoC 容器 ​

本指南涵盖 AdonisJS 中的依赖注入和 IoC 容器。你将了解到：

  • 如何使用 @inject 装饰器自动解析依赖
  • 构造函数注入和方法注入的区别
  • 何时以及如何手动使用 IoC 容器
  • 如何为复杂依赖注册绑定和单例
  • 如何使用抽象类实现适配器模式
  • 如何在测试期间替换依赖

概述 ​

依赖注入是一种设计模式，消除了手动创建和管理类依赖的需要。你不需要在类内部创建依赖，而是将它们声明为构造函数参数或方法参数，IoC 容器会自动解析它们。

AdonisJS 包含一个强大的 IoC（控制反转）容器，在整个应用中处理依赖注入。当你将类作为依赖进行类型提示时，容器会自动创建该类的实例并将其注入到需要的地方。

IoC 容器已经集成到 AdonisJS 的核心部分，包括控制器、中间件、事件监听器和 Ace 命令。这意味着你可以在这些类中类型提示依赖，当框架构造它们时会自动解析。

TIP

AdonisJS 使用 TypeScript 的 experimentalDecorators 和 emitDecoratorMetadata 编译器选项来启用依赖注入。这些选项已预配置在新 AdonisJS 项目的 tsconfig.json 文件中。

你的第一个依赖注入 ​

让我们从一个实际示例开始。我们将创建一个 AvatarService，为用户生成 Gravatar URL，然后将其注入到控制器中。

步骤 1：创建服务 ​

首先，创建一个将被注入的服务类。此服务根据用户电子邮件地址生成 Gravatar 头像 URL。

ts
import User from '#models/user'
import { createHash } from 'node:crypto'

export class AvatarService {
  protected getGravatarAvatar(user: User) {
    const emailHash = createHash('md5').update(user.email).digest('hex')
    const url = new URL(emailHash, 'https://gravatar.com/avatar/')

    url.searchParams.set('size', '200')
    return url.toString()
  }

  getAvatarFor(user: User) {
    return this.getGravatarAvatar(user)
  }
}

步骤 2：将服务注入控制器 ​

接下来，创建一个使用 AvatarService 的控制器。@inject() 装饰器告诉容器自动解析并注入该服务。

ts
import { inject } from '@adonisjs/core'
import type { HttpContext } from '@adonisjs/core/http'
import { AvatarService } from '#services/avatar_service'
import User from '#models/user'

@inject()
export default class UsersController {
  /**
   * 当此控制器被构造时，容器会自动注入
   * AvatarService
   */
  constructor(protected avatarService: AvatarService) {}

  async store({ request }: HttpContext) {
    /**
     * 创建新用户（为演示简化）
     */
    const user = await User.create(request.only(['email', 'username']))

    /**
     * 使用注入的服务生成并保存头像 URL
     */
    const avatarUrl = this.avatarService.getAvatarFor(user)
    user.avatarUrl = avatarUrl
    await user.save()

    return user
  }
}

步骤 3：注册路由 ​

最后，将控制器连接到路由。当你访问此端点时，AdonisJS 会自动使用容器构造控制器。

ts
import router from '@adonisjs/core/services/router'
import { controllers } from '#generated/controllers'

router.post('/users', [controllers.Users, 'store'])

@inject() 装饰器在控制器类上是必需的。没有它，容器不会知道要解析依赖。该装饰器使用 TypeScript 的反射能力在运行时检测构造函数依赖。

方法注入 ​

方法注入的工作方式与构造函数注入类似，但不是为整个类解析依赖，而是容器为特定方法解析依赖。当只有一个方法需要特定依赖，或你想保持类构造函数简单时，这很有用。

使用方法注入时，@inject() 装饰器必须放在方法之前。

ts
import { inject } from '@adonisjs/core'
import { HttpContext } from '@adonisjs/core/http'
import { AvatarService } from '#services/avatar_service'
import User from '#models/user'

export default class UsersController {
  /**
   * 方法上的 @inject 装饰器告诉容器
   * 自动解析 avatarService 参数
   */
  @inject()
  async store({ request }: HttpContext, avatarService: AvatarService) {
    const user = await User.create(request.only(['email', 'username']))

    /**
     * 直接作为方法参数使用注入的服务
     */
    const avatarUrl = avatarService.getAvatarFor(user)
    user.avatarUrl = avatarUrl
    await user.save()

    return user
  }
}

注意 HttpContext 始终是控制器方法的第一个参数，后面跟你想注入的任何依赖。容器会自动区分 HTTP 上下文和可注入依赖。

什么可以被注入？ ​

你只能在一个类中类型提示和注入类。由于 TypeScript 类型和接口在编译时被移除，对运行时代码不可见，因此容器无法解析它们。

如果类有其他无法自动解析的依赖（如配置对象），你必须在容器中将该类注册为绑定。我们将在本指南后面介绍绑定。

import type 陷阱 ​

导致依赖注入静默失败的常见问题是类意外地使用 TypeScript 的 import type 语法导入。这经常发生，因为具有自动导入功能的代码编辑器通常默认将类作为类型导入。

当你使用 import type 时，TypeScript 在编译期间完全剥离导入。容器在运行时没有类构造函数可解析，因此你的依赖变为 undefined。

ts
import { inject } from '@adonisjs/core'
import type { AvatarService } from '#services/avatar_service'

@inject()
export default class UsersController {
  constructor(protected avatarService: AvatarService) {}
}
ts
import { inject } from '@adonisjs/core'
import { AvatarService } from '#services/avatar_service'

@inject()
export default class UsersController {
  constructor(protected avatarService: AvatarService) {}
}

哪些类支持依赖注入 ​

以下类由容器自动构造，允许你使用构造函数注入，在某些情况下也可以使用方法注入。

类类型构造函数注入方法注入
控制器✅✅
中间件✅❌
事件监听器✅✅（仅 handle 方法）
Bouncer 策略✅❌
转换器❌✅
Ace 命令❌✅（仅生命周期方法）

对于你创建的任何其他类，你需要手动使用容器来构造它们，我们将在下一节介绍。

手动使用容器 ​

虽然 AdonisJS 自动使用容器构造控制器、中间件和其他框架类，但在某些场景下你可能需要手动构造自己的类。例如，如果你正在实现队列系统并希望每个任务类都受益于依赖注入，你需要直接使用容器的 API。

使用 container.make 构造类 ​

container.make 方法接受类构造函数并返回其实例，自动解析所有标记了 @inject() 的构造函数依赖。

让我们用队列任务场景来演示。我们将创建两个服务：

  • 一个用于日志记录的 LoggerService，以及一个依赖它的 UserService。
  • 然后在队列任务中手动使用容器来构造 UserService，它会自动解析其 LoggerService 依赖。

容器实例通过 app 服务在整个 AdonisJS 应用中可用。

ts
import { inject } from '@adonisjs/core'

class LoggerService {
  log(message: string) {
    console.log(message)
  }
}

@inject()
export class UserService {
  constructor(protected logger: LoggerService) {}

  createUser(data: any) {
    this.logger.log('Creating user...')
  }
}
ts
import app from '@adonisjs/core/services/app'
import { UserService } from '#services/user_service'

export default class ProcessUserJob {
  async handle(userData: any) {
    /**
     * 使用容器手动构造 UserService。
     * 其 LoggerService 依赖会自动解析。
     */
    const userService = await app.container.make(UserService)
    await userService.createUser(userData)
  }
}

容器递归解析整个依赖树。如果 UserService 有依赖，而那些依赖又有自己的依赖，容器会全部自动解析。

使用 container.call 调用方法 ​

你可以使用 container.call 方法对任何类方法执行方法注入。当你想要依赖注入到特定方法而不是整个类时，这很有用。

container.call 方法接受类实例、方法名称和运行时值数组。运行时值作为初始参数传递，后面跟任何自动解析的依赖。

ts
import { inject } from '@adonisjs/core'

class EmailService {
  send(to: string, message: string) {
    console.log(`Sending email to ${to}`)
  }
}

export class NotificationService {
  @inject()
  notify(userId: string, message: string, emailService: EmailService) {
    emailService.send(`user-${userId}@example.com`, message)
  }
}
ts
import app from '@adonisjs/core/services/app'
import { NotificationService } from '#services/notification_service'

/**
 * 创建服务实例
 */
const notificationService = await app.container.make(NotificationService)

/**
 * 使用容器调用方法。
 *
 * EmailService 自动解析并注入。
 * 前两个参数是我们提供的运行时值。
 */
await app.container.call(
  notificationService,
  'notify',
  ['user-123', 'Welcome to our platform!']
)

绑定 ​

当类需要无法通过 @inject() 装饰器自动解析的依赖时，绑定就是你使用的机制。例如，当一个类需要配置对象或原始值以及其类依赖时。

当类存在绑定时，容器会禁用其自动解析逻辑，改为使用你的工厂函数创建实例。

创建绑定 ​

绑定必须注册在服务提供者的 register 方法中。你可以使用 node ace make:provider 命令创建新的提供者。

步骤 1：定义需要自定义构造的类 ​

让我们创建一个需要 RedisConnection 和配置对象的 Cache 类。由于我们将此类注册为绑定，因此不需要使用 @inject 装饰器。容器将使用我们的工厂函数代替。

ts
import type { RedisConnection } from '@adonisjs/redis'

export type CacheConfig = {
  ttl: string | number
  grace: boolean
}

export class Cache {
  constructor(
    public store: RedisConnection,
    public config: CacheConfig
  ) {}

  async get(key: string) {
    // 缓存实现
  }

  async set(key: string, value: any) {
    // 缓存实现
  }
}

步骤 2：在提供者中注册绑定 ​

创建一个提供者并在其 register 方法中注册绑定。工厂函数接收一个解析器，可以创建其他类的实例。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import redis from '@adonisjs/redis/services/main'
import { Cache } from '#services/cache'

export default class CacheProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    this.app.container.bind(Cache, async (resolver) => {
      /**
       * 从容器解析 redis 依赖
       */
      const redis = await resolver.make('redis')
      const store = redis.connection()

      /**
       * 从应用配置获取配置
       */
      const config = this.app.config.get<CacheConfig>('cache')

      /**
       * 手动构造并返回带有所有依赖的
       * Cache 实例
       */
      return new Cache(store, config)
    })
  }
}

步骤 3：使用绑定 ​

容器使用你的工厂函数而不是尝试自动解析依赖。

ts
import app from '@adonisjs/core/services/app'
import { Cache } from '#services/cache'

const cache = await app.container.make(Cache)

await cache.set('user:1', { name: 'Virk' })
const user = await cache.get('user:1')

绑定让你完全控制类的构造方式。工厂函数接收一个解析器，你可以用它来创建其他依赖，允许你用自定义逻辑构建复杂的依赖树。

单例 ​

单例是只构造一次然后缓存的绑定。多次调用 container.make 获取单例会返回同一个实例。这对于应跨应用共享的服务很有用，如数据库连接或缓存层。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import redis from '@adonisjs/redis/services/main'
import { Cache } from '#services/cache'

export default class CacheProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    /**
     * 使用 singleton 而不是 bind。
     * Cache 实例将被创建一次并重用。
     */
    this.app.container.singleton(Cache, async (resolver) => {
      const redis = await resolver.make('redis')
      const store = redis.connection()
      const config = this.app.config.get<CacheConfig>('cache')
      return new Cache(store, config)
    })
  }
}

现在每次调用 app.container.make(Cache) 都返回完全相同的 Cache 实例，使其高效并在需要时确保共享状态。

别名 ​

别名为绑定提供替代的基于字符串的名称，允许你使用描述性名称而不是类构造函数来请求依赖。

要创建别名，使用 container.alias() 注册它，并使用 TypeScript 模块扩充更新 ContainerBindings 接口以实现类型安全。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import redis from '@adonisjs/redis/services/main'
import { Cache } from '#services/cache'

/**
 * 为 TypeScript 声明别名类型
 */
declare module '@adonisjs/core/types' {
  interface ContainerBindings {
    cache: Cache
  }
}

export default class CacheProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    /**
     * 将 Cache 绑定注册为单例
     */
    this.app.container.singleton(Cache, async (resolver) => {
      const store = redis.connection()
      const config = this.app.config.get<CacheConfig>('cache')
      return new Cache(store, config)
    })

    /**
     * 创建别名以便我们可以通过字符串 'cache' 引用 Cache
     */
    this.app.container.alias('cache', Cache)
  }
}

现在你可以使用字符串别名请求缓存。TypeScript 会知道 app.container.make('cache') 返回 Cache 实例，为你提供完整的自动补全和类型检查。

ts
import app from '@adonisjs/core/services/app'

/**
 * 使用字符串别名而不是类来请求缓存
 */
const cache = await app.container.make('cache')

绑定现有值 ​

有时你已经有了一个实例，并想直接将其注册到容器，而不是提供工厂函数。bindValue 方法将现有值绑定到类构造函数或别名，容器在每次请求时都返回该确切值。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import { Config } from '#services/config'

export default class AppProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    /**
     * 使用特定配置自己创建实例
     */
    const config = new Config({
      environment: 'production',
      debug: false,
    })

    /**
     * 直接绑定现有实例。
     * 每次请求 Config 都返回这个确切对象。
     */
    this.app.container.bindValue(Config, config)
  }
}

与接受工厂函数的 bind 或 singleton 不同，bindValue 接受实例本身。当你需要注册在容器外部创建的对象时（如在启动时解析的配置对象或从外部库接收的实例），这很有用。

bindValue 方法也可用于请求作用域解析器，这就是 HttpContext 和 Logger 等请求特定实例在 HTTP 请求期间注册的方式。示例请参阅 HTTP 请求期间的依赖注入。

HTTP 请求期间的依赖注入 ​

HttpContext 对象为每个 HTTP 请求接收一个隔离的容器解析器。这允许你注册仅在该特定请求持续期间存在的单例实例，这对于日志记录器或用户会话等请求作用域服务很有用。

这些请求作用域绑定应注册在 app/middleware/container_bindings_middleware.ts 文件中，该文件已预创建并自动注册在新的 AdonisJS 应用中。

ts
import { HttpContext } from '@adonisjs/core/http'
import type { NextFn } from '@adonisjs/core/types/http'
import { Logger } from '@adonisjs/core/logger'

export default class ContainerBindingsMiddleware {
  handle(ctx: HttpContext, next: NextFn) {
    /**
     * 将 HttpContext 本身注册为绑定。
     * 任何类型提示 HttpContext 的类都将接收
     * 当前请求的这个确切上下文实例。
     */
    ctx.containerResolver.bindValue(HttpContext, ctx)

    /**
     * 注册请求特定的日志记录器。
     * 在此请求期间解析的依赖 Logger 的所有类
     * 都将接收此日志记录器实例。
     */
    ctx.containerResolver.bindValue(Logger, ctx.logger)

    return next()
  }
}

在当前 HTTP 请求期间，任何类型提示 HttpContext 或 Logger 作为依赖的类都将接收此处注册的确切实例。这确保请求特定数据的一致性和正确作用域。

抽象类作为接口 ​

由于 TypeScript 接口在运行时被移除，你不能用它们来类型提示依赖。但是，你可以使用抽象类来实现相同的多态行为。这使你能够实现适配器设计模式，其中多个实现符合共同契约。

让我们构建一个可以与不同支付提供商配合使用的支付系统，同时保持你的业务逻辑与提供商无关。

定义契约 ​

首先，创建一个抽象类，定义所有支付提供商必须实现的契约。这充当你的接口，但在运行时仍然可用于容器作为注入令牌。

ts
/**
 * 抽象类充当接口。
 * 不同的支付提供商将实现它。
 */
export default abstract class PaymentService {
  abstract charge(amount: number): Promise<void>
  abstract refund(amount: number): Promise<void>
}

创建具体实现 ​

现在为不同的支付提供商创建具体实现。每个提供商用其特定逻辑实现抽象类的方法，但它们都符合相同的契约。

ts
import PaymentService from './payment_service.js'

export default class StripeProvider implements PaymentService {
  async charge(amount: number) {
    console.log(`Charging ${amount} via Stripe`)
  }

  async refund(amount: number) {
    console.log(`Refunding ${amount} via Stripe`)
  }
}
ts
import PaymentService from './payment_service.js'

export default class PaypalProvider implements PaymentService {
  async charge(amount: number) {
    console.log(`Charging ${amount} via PayPal`)
  }

  async refund(amount: number) {
    console.log(`Refunding ${amount} via PayPal`)
  }
}

注意两个实现都遵循完全相同的契约。你的应用代码可以依赖 PaymentService 而不知道正在使用哪个具体提供商。

配置使用哪个实现 ​

注册一个绑定，告诉容器当有人请求抽象 PaymentService 时要注入哪个具体实现。这是你决定应用使用 Stripe、PayPal 还是任何其他提供商的地方。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import PaymentService from '#services/payment_service'
import StripeProvider from '#services/stripe_provider'

export default class AppProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    /**
     * 将抽象 PaymentService 绑定到具体 StripeProvider。
     * 任何类型提示 PaymentService 的类都将接收 StripeProvider。
     */
    this.app.container.bind(PaymentService, () => {
      return new StripeProvider()
    })
  }
}

在代码中使用抽象 ​

现在你的业务逻辑可以依赖抽象 PaymentService 而不与任何特定提供商耦合。

ts
import { inject } from '@adonisjs/core'
import { HttpContext } from '@adonisjs/core/http'
import PaymentService from '#services/payment_service'

export default class CheckoutController {
  /**
   * 类型提示抽象 PaymentService。
   * 容器注入 StripeProvider（基于我们的绑定）。
   */
  @inject()
  async store({ request }: HttpContext, paymentService: PaymentService) {
    const amount = request.input('amount')

    /**
     * 我们在 PaymentService 上调用方法，但实际
     * 实现是 StripeProvider。我们的代码不知道
     * 也不关心使用哪个提供商。
     */
    await paymentService.charge(amount)

    return { success: true }
  }
}

这个模式的力量在于其灵活性。要从 Stripe 切换到 PayPal，你只需要在 AppProvider 中将绑定从 new StripeProvider() 改为 new PaypalProvider()。你的控制器和所有其他业务逻辑完全不变。这种分离使你的代码更可维护和可测试。

上下文依赖 ​

上下文依赖允许你根据请求它的类注入同一抽象类的不同实现。当应用的不同部分需要同一服务的不同配置或实现时，这很有用。

建立在上一节的 PaymentService 示例上，想象你对应用的不同部分有不同的业务需求。用户订阅应通过 Stripe 处理（用于经常性计费功能），而一次性产品购买应通过 PayPal 处理（用于更广泛的支付方式支持）。

设置具有不同需求的服务 ​

让我们创建两个都需要 PaymentService 的服务，但它们应根据特定业务需求使用不同的支付提供商。

ts
import { inject } from '@adonisjs/core'
import PaymentService from '#services/payment_service'

@inject()
export default class SubscriptionService {
  /**
   * SubscriptionService 将接收为 Stripe 配置的
   * PaymentService 实例（用于经常性计费）
   */
  constructor(protected paymentService: PaymentService) {}

  async createSubscription(userId: number, plan: string) {
    await this.paymentService.charge(999)
  }
}
ts
import { inject } from '@adonisjs/core'
import PaymentService from '#services/payment_service'

@inject()
export default class OrderService {
  /**
   * OrderService 将接收为 PayPal 配置的
   * PaymentService 实例（用于一次性购买）
   */
  constructor(protected paymentService: PaymentService) {}

  async createOrder(userId: number, items: any[]) {
    await this.paymentService.charge(2499)
  }
}

两个服务都类型提示 PaymentService，但它们需要不同的实现。没有上下文依赖，你只能全局绑定一个提供商，迫使两个服务使用相同的实现。

注册上下文绑定 ​

在服务提供者中使用 when().asksFor().provide() API 注册上下文依赖。这告诉容器当特定类请求依赖时，提供特定实现。

ts
import type { ApplicationService } from '@adonisjs/core/types'
import PaymentService from '#services/payment_service'
import StripeProvider from '#services/stripe_provider'
import PaypalProvider from '#services/paypal_provider'
import SubscriptionService from '#services/subscription_service'
import OrderService from '#services/order_service'

export default class AppProvider {
  constructor(protected app: ApplicationService) {}

  register() {
    /**
     * 当 SubscriptionService 请求 PaymentService 时，
     * 提供 Stripe 实现（用于经常性计费）
     */
    this.app.container
      .when(SubscriptionService)
      .asksFor(PaymentService)
      .provide(() => {
        return new StripeProvider()
      })

    /**
     * 当 OrderService 请求 PaymentService 时，
     * 提供 PayPal 实现（用于一次性购买）
     */
    this.app.container
      .when(OrderService)
      .asksFor(PaymentService)
      .provide(() => {
        return new PaypalProvider()
      })
  }
}

现在 SubscriptionService 在构造时自动接收 StripeProvider，而 OrderService 接收 PaypalProvider，都通过相同的 PaymentService 类型提示。这使你的服务代码保持干净并专注于业务逻辑，同时让你根据上下文精细控制注入哪些依赖。

上下文绑定模式与上一节的适配器模式结合使用时特别强大。每个服务对其使用的支付提供商完全不可知，但每个都获得其特定用例所需的确切实现。

解析优先级 ​

当容器解析依赖时，它按特定顺序检查多个来源。理解此优先级有助于你预测将注入哪个实现并调试意外行为。

容器按以下顺序解析依赖，在第一个匹配处停止：

优先级来源描述
1替换使用 container.swap() 注册的测试覆盖
2上下文绑定使用 when().asksFor().provide() 注册的绑定
3解析器值绑定到作用域解析器的值（例如请求作用域绑定）
4容器值使用 container.bindValue() 注册的值
5容器绑定使用 container.bind() 或 container.singleton() 注册的工厂函数
6自动构造容器使用 @inject() 自行构造类

替换具有最高优先级，因为它们是为测试设计的。当你替换依赖时，无论任何其他绑定，你都希望使用假实现。这确保你的测试保持隔离和可预测。

上下文绑定排在其次，因为它们代表有意的、上下文特定的覆盖。当你明确说"当 ClassA 请求 ServiceB 时，提供这个特定实现"，该意图应覆盖一般绑定。

如果没有替换或上下文绑定匹配，容器检查绑定到当前解析器作用域的值。在 HTTP 请求期间，HttpContext 和请求作用域的 Logger 以这种方式绑定，确保每个请求获得自己的实例。

容器级值和绑定接下来被检查。这些是你在服务提供者中注册的应用范围单例和工厂。

最后，如果完全不存在绑定，容器尝试自动构造。它使用 TypeScript 的反射元数据识别标记了 @inject() 的构造函数依赖并递归解析它们。

此优先级顺序意味着你可以分层配置依赖：在提供者中定义一般绑定，为特定类上下文地覆盖它们，并在测试期间完全替换它们——所有这些都无需修改原始代码。

在测试期间替换依赖 ​

容器提供一个直接的 API 用于在测试期间用假实现替换依赖。这允许你隔离测试代码而不访问真实外部服务。

container.swap 方法用临时实现替换绑定，container.restore 将其恢复为原始值。在替换期间，代码库中任何类型提示被替换类的部分都将接收假实现。

ts
import { test } from '@japa/runner'
import app from '@adonisjs/core/services/app'
import UserService from '#services/user_service'

test('get all users', async ({ client, cleanup }) => {
  /**
   * 创建一个扩展现有服务的假实现
   */
  class FakeUserService extends UserService {
    /**
     * 覆盖 all() 方法以返回假数据
     * 而不是查询数据库
     */
    all() {
      return [
        { id: 1, username: 'virk', email: 'virk@adonisjs.com' },
        { id: 2, username: 'romain', email: 'romain@adonisjs.com' }
      ]
    }
  }

  /**
   * 用我们的假实现替换 UserService。
   * 在此测试期间解析 UserService 的任何代码
   * 都将接收 FakeUserService。
   */
  app.container.swap(UserService, () => {
    return new FakeUserService()
  })

  /**
   * 测试完成后恢复原始绑定。
   * cleanup 钩子确保即使测试失败也会运行。
   */
  cleanup(() => app.container.restore(UserService))

  /**
   * 发起 HTTP 请求。控制器将接收
   * FakeUserService，它返回我们的假数据。
   */
  const response = await client.get('/users')

  response.assertStatus(200)
  response.assertBodyContains({
    users: [
      { username: 'virk' },
      { username: 'romain' }
    ]
  })
})

当你测试依赖外部 API、支付网关、邮件服务或任何你不想在自动化测试期间交互的资源的代码时，替换特别有价值。假实现可以模拟各种场景（成功、失败、边缘情况）而无需真实基础设施。

容器事件 ​

容器在解析绑定时发出事件，允许你观察和响应依赖解析。这对于调试、监控或实现横切关注点很有用。

容器发出单一事件类型：container_binding:resolved。每次容器成功解析类实例时触发此事件，无论是通过自动解析、绑定还是单例。

你可以使用应用的事件发射器监听此事件。

ts
import emitter from '@adonisjs/core/services/emitter'

emitter.on('container_binding:resolved', (event) => {
  /**
   * event.binding 包含被解析的类构造函数
   * 或字符串别名
   */
  console.log('Resolved binding:', event.binding)

  /**
   * event.value 包含创建的实际实例
   */
  console.log('Instance:', event.value)
})

事件对象提供两个属性。首先，event.binding 包含被解析的绑定键（类构造函数或字符串别名）。其次，event.value 包含容器创建并返回的实际实例。

每次解析都会触发此事件，包括嵌套依赖。例如，如果容器解析 UserService，它依赖 LoggerService，你将收到两个事件：一个用于 LoggerService，一个用于 UserService。
